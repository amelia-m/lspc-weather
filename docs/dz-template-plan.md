# Plan: a template repository any drop zone can use

Draft, 2026-11-22, at the maintainer's word ("a repo based on this one that is designed for any drop zone to use it as a template to create their own custom weather page"); revised 2026-11-23 after two fresh agents' reviews of the repo and the draft, the second after the first's edits were in (their checked facts carry that date below). Nothing here is built. The decisions under "For the maintainer" come first.

## Goal and non-goals

**Goal.** A GitHub template repository. A DZ clicks "Use this template", fills in one configuration file (its coordinates, elevation, name, exit altitudes, its own posted wind limits, a few facts about how it jumps), runs one setup command that finds its stations from the coordinates, and gets a dashboard like this one deployed to GitHub Pages, with the same rule: every flag rests on a published source or a plain observed fact, and the app gives no verdict.

**Non-goals, for the first version.** Not a hosted multi-tenant site (each DZ owns its deploy, its data and its citations review). Not outside the United States: every observation and forecast source here is NWS, NOAA or IEM, and 14 CFR and the USPA SIM are the rulebook; a non-US DZ needs other sources and other citations, a different project. Alaska and Hawaii are a decision below: IEM's ids there are the NWS ids whole (AK_ASOS: 205 four-character sids, read 2026-11-23), so the id rule differs. Not this repository's research apparatus (below).

## The setup command

`npm run setup` reads `dz.config.json`, which the DZ writes and the command never overwrites: name, short name, airport ident or null, lat and lon (four decimals; the points endpoint normalises more to four, seen 2026-11-23), elevation with source and date, exit altitudes `{ highest, lowest }` ft AGL with source and date, the winds table's top, time zone (optional), repo URL, the Pages origin, relay URL (null), page-count endpoint (null), waiver tiers with their citation, facts, and optional overrides for any station the lookups choose (printed as "set by hand").

It writes `dz.derived.json`, committed, every field as `{ value, from: { url, readAt, field } }`, and prints one table: field, value, the URL it came from, and the rule that chose it (the counts and distances below, 12 stations, 90 minutes, 150 mi, three TAF stations, the military-name list, are the plan's own choices: they pick sources, not flags, so the governing rule does not bind them, but a DZ should see them). It runs under Vitest, not `tsx` (the app's fetch code reads `import.meta.env` at load and throws under tsx), sends a User-Agent naming the DZ's repo, and retries once on a timeout, reset, 502, 503 or 504 with `scripts/liveFetch.ts`, not `fetchJson`. The lookups, in order (each endpoint read 2026-11-23 for this DZ's point):

1. **Point.** `api.weather.gov/points/{lat},{lon}`: `gridId`, `gridX`, `gridY` (OAX 77,42), `forecastZone`, `county`, `timeZone`, `radarStation` (KOAX), `observationStations` (a URL), `relativeLocation` (city and state). Not 200: stop; a point outside NWS coverage is the non-US case.
2. **Candidate stations.** The `observationStations` URL (`gridpoints/OAX/77,42/stations`): one page, a fixed set (47 stations here; its `pagination.next` names 48 ids and answers none), reaching about 180 mi and four WFOs, which covers the TAF chain's 150 mi. Each with id, name, coordinates, elevation, time zone, forecast zone. It crosses the state line (KCBF and KSDA in Iowa) and is only roughly nearest-first (KAFK at 23.1 mi before KMLE at 22.5), so re-sort by `haversineMiles` from the DZ. One request, no border logic.
3. **Live stations.** For each state among the nearest 12 (the forecast zone's first two letters), IEM's `api/1/currents.json?network={ST}_ASOS`: every station's `utc_valid` and raw METAR in one request. Keep those with a report in the last 90 minutes (AWOS every 20, with room for a gap). NWS's `stations/{id}/observations/latest` is the cross-check, not the source: on 2026-11-23 it served K04V with an empty `rawMessage` and an empty decode while IEM had the 04:35Z report in full, the same weak feed the app itself reads second.
4. **IEM id and network.** Per state, `mesonet.agron.iastate.edu/geojson/network/{ST}_ASOS.geojson` (NE: 47 features with `sid`, `network`, `online`, `elevation`, `tzname`, and attributes `IS_AWOS`, `HASTAF`). One underscore: `NE__ASOS` is Niger (599 networks listed, 266 `_ASOS`). Match from the NWS list into IEM on the id with a leading K stripped: K04V is sid `04V` (CO_ASOS, read 2026-11-23), and IEM carries ids NWS serves under no K-station (0CO, 1NW, 5SM), so never match the other way. No match: `iemId: null`, and the app needs a code path for a station IEM does not carry.
5. **Observation station.** The nearest kept station with an IEM match and `online`. A tie within a mile: ASOS over AWOS, then the newer report. **Nearby METARs:** the next five by distance. Two states need no second request: `currents.json` takes `wfo=` and `state=` (its openapi.json, read 2026-11-23; `wfo=OAX&networkclass=ASOS` answered 22 records over NE_ASOS and IA_ASOS), so the change in `fetchIemNetwork` is the query, and the setup records the WFO or states used.
6. **TAF chain.** `products/types/TAF/locations` once (706 codes; OMA and LNK present, OFF and PMV absent); a kept station issues an NWS TAF when its id without K is a key; cross-check IEM's `HASTAF` (NE: twelve stations, OFF absent) and print a disagreement. The chain is the nearest three within 150 mi. A kept station nearer than the first whose name holds AFB, AAF, NAS, MCAS or Air Force is listed as a relay candidate: a TAF only aviationweather.gov carries, which CI cannot check (that host sends no CORS header and answered the sandbox 403 on 2026-11-23). None within 150 mi: an empty chain, printed, not a failure.
7. **Radar.** `radarStation` from the point, confirmed against `radar/stations` (208 features with `stationType`, coordinates, elevation) for name and coordinates; print the three nearest WSR-88D sites and say when NWS's choice is not the nearest; compute `DZ_ON_RADAR_IMAGE` and warn when it is null.
8. **No FD winds station.** The winds have one source: this repository dropped its NOAA FD fallback on 2026-11-23, NCEP's last CONUS bulletin having been issued 2026-11-03 (docs/open-questions.md, "Dropped: the FD winds fallback").
9. **Time zone.** The point's, checked against the observation station's and IEM's `tzname`; a disagreement is printed.
10. **Elevation.** Never derived. Print the observation station's elevation (KPMV 366.06 m, 1,201 ft, against 1,204 in `site.ts`) and the difference from the DZ; warn over 500 ft. A flag run once from the DZ's own address, not CI, fetches the winds request and records Open-Meteo's model `elevation` beside the field's (the Open-Meteo quota is per address).
11. **`setup:check`,** after deploy: one fetch of each configured source, the TAF chain through api.weather.gov, and with a relay set, its TAF and NBM paths. The NBM hourly bulletin of 2026-11-23 02Z held 9,589 station blocks, every NE_ASOS station among them, AWOS included (21 of NE's 47, KPMV one), 32 of Colorado's 33 AWOS, and K04V, so a relay 500 is a fault, not a missing station. Fails on the observation station and the gridpoint only; the rest is printed.

Tests: recorded answers under `tests/fixtures/setup/` (the point, the stations page, one IEM `currents` answer, one IEM network file, the TAF locations, the radar stations) and the choice rules on them, a two-state case and a tie among them.

## Phases

1. **Decisions** (the list below). Nothing else starts before the first three.
2. **Coordinates from the environment.** Make `scripts/schulzeCompare.live.ts` and the normaliser take coordinates and elevation from the environment, then run the comparison for a coastal point and a Mountain West point as a workflow (the pattern of `cloud-cover-fetch.yml`; Open-Meteo's quota keeps it out of the sandbox). The code-level part of the elevation risk is read already (below); this is the live check. The script reads `SITE` today.
3. **Carve out the core, in this repository first.** First the two schemas, `dz.config.json` and `dz.derived.json`, and a test-config loader, since the invented DZs need them before the setup command exists. Then move every LSPC value in the table above behind the config, one commit per row, each proven by the existing tests passing with LSPC's config and by two invented DZs rendering every card without an LSPC string: one at sea level with a 9,500 ft top exit and no waiver, one at about 5,000 ft with a military TAF nearby and the facts unknown. Both break the visibility row's current setting and the second breaks the table top (below). This is most of the work, and it improves this repo whether or not the template follows: the facts and tiers become data.
4. **The setup command**, with its fixture tests.
5. **The template repository.** A new repository from the core (history a decision below), marked as a template on GitHub, with: a README that is the setup guide; a `CLAUDE.md` that carries the governing rule and the consequences list, less the LSPC facts; the trimmed workflows; `relay/` as an optional folder nothing imports from; the citations page with the club citation blank until the DZ adds its document.
6. **Prove it.** Instantiate the template for the two invented DZs and for two real ones with public data, one coastal and one high; run the four gates and `scripts/liveSite.ts` against a local build at 1280, 390 and 320 px. Then instantiate LSPC from the template and diff its rendered pages against this app's on the same fixtures: any difference is either a research page, meant to be missing, or a lost behaviour.
7. **Keeping instances current.** One supported route: the instance adds the template as a remote and merges; the config lives in one folder, the relay's station constants included, so the merge is clean. Releases on the template tagged, with a changelog that says when a DZ must re-read a citation (a SIM edition change, say).

## Risks and open technical questions

- **Elevation and the winds table.** `normalize.ts` drops pressure levels below Open-Meteo's model `elevation` (not the field's), and `sampleAt` fills the bottom down from the 10 m sample. At sea level nothing breaks, only the comments about 1000 hPa being underground go stale. At 5,000 ft, 1000 to 850 hPa are underground and dropped every hour, 825 hPa (about 580 ft AGL) is the first kept with the 180 m sample under it, so no gap at the bottom; but 13,000 ft AGL is 18,000 ft MSL and 500 hPa stands near 18,300 ft in a standard atmosphere and lower in a cold trough, so the top row drops on those days. The level list must be a function of elevation (450 and 400 hPa above about 17,000 ft MSL at the top; whether Open-Meteo serves them with values is unchecked), and the "As Schulze" set then takes his higher levels. The drop is against Open-Meteo's `elevation`, not the field's, so the kept set changes by the hour with the pressure (harmless: the interpolation is sample-agnostic), and the app sends no `elevation=` parameter (an option it does not use). "As Schulze" keeps underground levels on purpose, so at 5,000 ft his Surface row is built through up to six underground levels filled from the lowest one above ground. In terrain the model datum can sit hundreds of feet from the field, which the card's gap note prints; the setup records both.
- **The visibility row** derives from the config: `both` when the highest exit plus elevation is at or above 10,000 ft MSL and the lowest is under it; the 5 SM row alone when even the lowest exit is at or above; the 3 SM row alone when even the highest is under. At sea level a 9,500 ft top exit is wholly in the 3 SM row, and `both` would fire at 4 SM on a row no exit reaches; at 5,000 ft a 5,500 ft hop-and-pop is 10,500 ft MSL, in the 5 SM row, and the hop-and-pop fact's claim is false. The three settings exist and every test passes with any of them (CLAUDE.md), so this is config plumbing, not a new flag; the hop-and-pop fact becomes a sentence derived from the lowest exit, keeping `source`, `date` and `claim`, which the `both` row's `#citations` asks interpolate. The flight-category comparison and the overcast guidance are generic.
- **The ceiling datum.** METAR and NBM ceilings are AGL at the station, and the overcast flag and the Ceiling & sky tables read them as the DZ's. KPMV is 22 ft higher than the field; a station several hundred feet above or below a DZ changes what 2,500 ft AGL means over it. The card should print the station-to-DZ elevation difference beside the distance (`#citations` already asks about the altimeter reduction).
- **No ASOS nearby.** Some DZs are 40 miles from a reporting station. The card's "Observed at X (N mi ENE)" line already says the distance; the template's README should say what the dashboard is worth at that distance and leave the choice to the DZ. A station IEM does not carry has no code path today.
- **Quotas** are per reader's browser, as now. Open-Meteo's free tier is per address and the weights are known (docs/open-meteo-terms.md); a DZ with many readers stays under it as this one does. The template's README carries the terms and the credit rule.
- **Support.** A template repo invites issues from other DZs. Whether the maintainer wants that is a decision, not a technical point.
